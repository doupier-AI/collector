# Collector 产品需求文档（PRD）

版本：2.0
日期：2026-06-13
状态：功能边界收束基线

## 1. 产品定位

Collector 是一款面向个人学习者的本地优先内容收集与 AI 整理工具。

它帮助用户在自由浏览、阅读、观看和使用 AI 的过程中，以尽可能低的操作成本保存零散材料；随后把这些材料整理为近期关注方向，并在用户明确选择后生成可追溯、可持续更新的专题整理文档。

一句话定位：

> 随手收集零散材料，在需要时把它们整理成一篇真正可用的专题文档。

Collector 只承诺完成两件事：

1. **优雅、高效地收集内容。**
2. **忠实地整理用户已经收集的材料。**

Collector 不替用户决定应该学习什么，也不以自动构建完整知识图谱为目标。

## 2. 用户问题

### 2.1 核心问题

用户在网页、AI 对话、视频字幕、本地文档等来源中不断发现值得保留的内容，但这些内容通常存在以下问题：

- 来源分散，保存入口不统一；
- 当下有价值，稍后却难以回忆收集原因；
- 单条内容过于零碎，逐条整理的成本高于其即时收益；
- 多条材料可能逐渐形成方向，但用户不愿持续维护标签和目录；
- 传统收藏只保存内容，不能交付可阅读、可使用的整理成果；
- 自动总结工具容易脱离原文、强行拼接主题或擅自扩展用户没有收集的知识。

### 2.2 产品机会

Collector 不要求用户在采集时完成分类，而是在积累后提供一个轻量中间层，帮助用户看见“最近收集的内容正在形成哪些方向”。当用户对某个方向产生明确兴趣时，再把相关材料整理为正式文档。

因此产品核心不是“管理知识条目”，而是缩短以下路径：

```text
发现有价值的内容
→ 无负担地保存
→ 看见近期关注方向
→ 选择值得整理的范围
→ 获得可追溯的专题文档
```

## 3. 目标用户与场景

### 3.1 首批目标用户

- 中国大陆的开发者、产品经理、研究型知识工作者；
- 经常使用浏览器、AI 对话、技术文章、PDF 或字幕材料；
- 学习路径容易发散，但不愿投入大量时间维护复杂笔记结构；
- 希望数据默认留在本地，同时愿意在明确授权下使用云模型。

### 3.2 核心场景

1. 用户在网页中看到一段有价值的内容，选中后右键收集，不中断当前浏览。
2. 用户在 AI 对话、本地文档或其他应用中复制内容，通过快捷键进入快速采集模式并提交。
3. 用户拖入 Markdown、TXT 或文本 PDF，保留原文件及可定位内容。
4. 用户稍后打开 Collector，快速了解近期材料形成了哪些方向。
5. 用户选中一个方向，保存为专题并生成一篇基于现有材料的整理文档。
6. 新材料出现后，系统提示可能属于已有专题；用户确认后再更新文档。

## 4. 产品原则

### 4.1 用户主导学习

- 用户决定收集什么、关注什么、何时生成文档。
- AI 可以整理、概括和提示材料边界，但不安排学习顺序。
- 缺口、建议和推荐不能自动转化为任务、进度或催促。
- 用户不需要维护系统推断出的知识关系。

### 4.2 收集优先于分类

- 采集时不要求选择专题、标签、模型、证据等级或处理方式。
- 网络、解析和模型失败不得导致原始内容丢失。
- 提交成功以本地持久化为准，不以 AI 处理完成为准。

### 4.3 原始材料可追溯

- 原始材料记录“用户收集到了什么”，不代表内容已经被证实。
- AI 生成内容不能覆盖原文或伪装成原文。
- 同一份原始材料只保存一次，可以被多个专题引用。
- 专题文档中的关键内容应能回到对应原文、网页、文件页码或用户粘贴记录。

### 4.4 整理忠于材料

- 默认产物是材料整理，不是通用教程。
- 不为了文章完整而无标识地混入模型记忆或外部信息。
- 无法确认的内容可以保留，但必须表达不确定性。
- 无关材料不得为了“形成文章”而被强行串联。

### 4.5 本地优先，云端受控

- 原始材料、专题、文档和应用状态默认保存在本地。
- 发送到云模型的内容必须可知、可关闭、可审计。
- AI 不可用时，采集、查看、编辑、删除和导出仍应可用。
- 产品不提供本地模型部署、下载或硬件运行功能；AI 整理统一使用用户明确配置并授权的外部供应商。

### 4.6 用户界面不暴露工程模型

`Capture`、`Artifact`、`Fragment`、`AgentRun`、L0-L3、证据等级、Prompt Version 等仅属于内部实现或诊断信息，不是普通用户需要理解的产品概念。

## 5. 核心知识形态

首版只向用户呈现四种形态。

| 形态 | 定义 | 生命周期 |
| --- | --- | --- |
| 原始材料 | 用户采集的文本、网页、文件或链接 | 长期保存，支持版本、回收站和溯源 |
| 近期收集 | AI 对近期材料形成的临时主题分组 | 动态计算，可随新材料变化 |
| 专题 | 用户明确保存的长期材料容器 | 稳定存在，只能由用户确认变更 |
| 专题文档 | 基于专题材料生成的正式整理成果 | 每个专题一篇主文档，保留版本历史 |

以下内容可以作为内部处理结果，但首版不成为用户管理的独立实体：

- 原文片段；
- 知识点；
- 概念；
- 主张；
- 语义关系；
- 模型推理过程。

## 6. 核心闭环

```text
网页右键 / 桌面粘贴 / 文件拖入
→ 原始材料立即保存
→ 本地解析、去重与来源记录
→ AI 在合适时机批量整理近期材料
→ 形成临时主题分组和一句话概括
→ 用户保存分组为专题，或选择材料创建专题
→ 用户触发专题文档生成
→ 系统集中核验文档中的关键结论
→ 生成带来源、带边界说明的版本化文档
→ 新材料到来时提示加入和更新，不自动改写
```

## 7. 功能需求

### 7.1 极简采集

#### 浏览器入口

- Chromium 扩展支持选中文字后右键“收集到 Collector”。
- 有选区时保存文字、URL、标题、采集时间、少量上下文和可用的定位信息。
- 无选区时允许收集当前网页，后端解析正文或使用扩展提交的正文快照。
- 成功后只显示轻量反馈，不打开主应用、不要求确认分类。
- 网络失败进入本地重试队列，重试不得重复创建材料。

#### 桌面入口

- `Ctrl+Shift+Space` 唤起主窗口并进入极简的快速采集模式。
- 快速采集模式只保留一个输入区域、附件入口、提交动作和低干扰状态反馈。
- 支持粘贴文本、URL，以及拖入 TXT、Markdown、文本 PDF 和常见图片。
- 图片首版只保存，不默认 OCR。
- `Ctrl+Enter` 提交，`Esc` 隐藏并保留草稿。
- 不主动读取或监听剪贴板，不使用 UI Automation 或模拟复制。
- 可提供将选中内容拖入 Collector 的增强交互，但不能作为唯一采集方式。

### 7.2 原始材料管理

- 支持查看、搜索、编辑、移入回收站、恢复和永久删除。
- 编辑必须保留修订历史，不能静默改写原始记录。
- 删除专题不会删除被其引用的原始材料。
- 删除原始材料前，提示哪些专题或文档引用会受到影响。
- 删除后相关文档不立即被整篇重建；系统标记引用缺失，等待用户决定是否更新。
- 文件保存 checksum，网页和文件尽可能保留精确定位。
- 粘贴且无来源说明的内容明确显示为“用户提供”，不得伪装成外部引用。

### 7.3 近期收集

“近期收集”是系统自动交付的轻量产物，用于回答：

- 我最近收集了什么？
- 哪些内容正在形成共同方向？
- 哪个方向值得我主动整理？

每个临时分组最多展示：

- 临时名称；
- 一句话概括；
- 包含的材料数量和最近新增数量；
- 代表性材料；
- 查看材料、保存为专题、生成专题文档等动作。

行为约束：

- 近期收集持续更新，不强制按自然日生成“每日文档”。
- 分组依据可以变化，但不得修改已固化专题。
- 无法可靠归类的材料保留为零散内容。
- 不为每条材料立即生成完整摘要、知识点和关系集合。
- 用户仅浏览分组不会自动创建专题。
- 分组不等于事实分类，也不建立永久语义关系。

### 7.4 专题

- 用户通过“保存为专题”或“生成专题文档”明确创建专题。
- 专题最小信息包括名称、已确认材料、待确认的新材料、主文档和版本历史。
- 同一份原始材料可以被多个专题引用，但底层只保存一份。
- 新材料与已有专题相似时，只生成加入建议，不自动加入。
- AI 可以建议重命名、拆分或合并，但不能直接改变专题。
- 首版不要求专题层级、复杂标签体系或专题之间的关系。

### 7.5 专题整理文档

专题文档是用户触发的主要成果，回答：

> 我收集的这些材料共同说明了什么？

默认能力：

- 根据材料内容组织合适的章节，而非机械套用固定模板；
- 去重并合并重复表达；
- 呈现共同观点、差异、限制和未解决问题；
- 为关键内容提供来源引用；
- 区分原材料表达、AI 整理和用户编辑；
- 在文末显示折叠的“材料缺口”，只呈现数量和可展开内容；
- 允许用户编辑，并保护用户修改不被后续更新覆盖；
- 每个专题首版只维护一篇主文档及版本历史。

文档不得：

- 默认扩写成完整课程或通用教程；
- 无标识地使用模型记忆补齐材料；
- 把来源不明的观点陈述为确定事实；
- 因材料缺口阻止用户生成文档；
- 在新材料到来时自动重写用户已经编辑的内容。

### 7.6 真实性核验

- 日常采集阶段不默认联网核验每条材料。
- 用户生成或更新专题文档时，系统集中识别并核验关键结论。
- 核验对象是进入正式文档的重要陈述，而非所有原文句子。
- 核验结果采用自然语言表达，如“获得多个来源支持”“存在不同说法”“可能过时”“尚无足够依据”。
- 核验失败或结果不确定不阻止文档生成。
- 默认不自动修改原材料，只在文档中呈现依据状态。
- 联网核验必须遵守用户的长期授权策略，并保留查询与来源记录。

### 7.7 新材料与文档更新

```text
新材料到达
→ 系统建议可能属于某个专题
→ 用户接受或忽略
→ 专题显示“有新材料可整理”
→ 用户预览影响范围
→ 用户触发生成新版本
```

- 默认执行增量补充，尽量维持原有结构。
- 全文重写必须由用户明确选择。
- 用户编辑过的段落默认受保护。
- 更新前后应能查看差异并回退版本。

### 7.8 模型调用与成本监控

- 原始保存、本地解析、去重和基本来源提取不依赖云模型。
- AI 整理采用延迟和批量处理，避免每新增一条材料就重写全部结果。
- 批处理可以由材料积累、空闲时间、用户打开近期收集或“立即整理”触发。
- 具体阈值属于可调策略，不进入用户的主要操作流程。
- 用户可选择“及时、均衡、节省”三种整理节奏，不暴露内部 token 阈值。

必须记录：

- 供应商与模型；
- 输入和输出 token；
- 估算费用；
- 调用用途；
- 延迟、成功率、重试次数和脱敏错误；
- 立即处理与批量整理的成本分类。

用户可在设置中查看本月调用量、费用、成功率、模型分布和预算提醒。技术明细默认不出现在采集和阅读流程中。

### 7.9 数据与云模型控制

- 用户可以保存多个外部供应商 Profile，并明确选择一个活动模型；DeepSeek 不作为独立产品模块。
- 所有供应商 Key 由 Electron Main Process 通过 `safeStorage` 保存，Renderer、SQLite、日志和导出文件不得保存明文 Key。
- 内置供应商使用登记的官方地址；自定义 OpenAI-compatible 或 Anthropic-compatible 地址只允许公网 HTTPS。
- 首次启用云模型前说明哪些数据会被发送。
- 用户可以对单条材料禁用云端处理。
- 应提供数据导出、备份和本地存储位置说明。
- 云模型失败不得污染专题或文档的有效版本。

## 8. 信息架构

### 8.1 应用壳与快速采集

Collector 在操作系统中呈现为一个完整应用，而不是三个相互独立的产品窗口。

- 工作台、专题、全部材料和设置位于同一个主窗口内，通过应用内导航切换；
- 全局快捷键唤起同一主窗口的“快速采集”紧凑模式；
- 当主窗口已经打开时，快速采集以窗口内聚焦状态呈现，不再创建第二个独立窗口；
- 提交或取消后恢复用户此前所在页面，避免丢失工作上下文；
- 托盘菜单只负责唤起应用并导航到对应页面，不创建新的工作台或设置窗口。

快速采集状态只包含：

- 一个主要输入区；
- 附件入口；
- 提交动作；
- 简短状态与撤销入口；
- 返回主界面的低视觉权重入口。

### 8.2 主界面

一级导航首版只保留：

- **近期收集**：动态分组、零散材料和待处理状态；
- **专题**：用户已经固化的专题及主文档；
- **全部材料**：搜索、查看和执行基础增删改查。

模型运行、证据片段、错误堆栈等进入折叠的诊断区域，不占据一级导航。

### 8.3 设置页面

- 通用：快捷键、开机启动、窗口行为；
- AI：供应商、授权、Key 状态、整理节奏、用量和预算；
- 数据：本地位置、备份、导入、导出和回收站；
- 实验能力：仅在真实可用时出现，不长期放置大量占位页面。

## 9. 首版功能边界

### 9.1 必须完成

1. 网页选区和整页入口可靠采集。
2. 桌面粘贴、URL 和支持文件的可靠采集。
3. 原始材料查看、搜索、编辑、回收站、恢复和删除。
4. 文本、Markdown、文本 PDF 和网页正文的本地解析与引用定位。
5. 延迟批量形成近期收集分组和一句话概括。
6. 用户固化分组为专题，并管理专题材料。
7. 每个专题生成一篇带引用的版本化整理文档。
8. 文档生成时对关键结论集中核验，失败不阻塞生成。
9. 新材料加入与文档更新采用用户确认机制。
10. 模型 token、费用、调用用途和失败情况可监控。
11. 本地存储、云模型授权和 Key 安全边界完整。

### 9.2 明确不做

- 用户可维护的独立知识点实体；
- 固定或开放式的永久知识关系；
- 知识图谱和以距离代表客观语义关系的版图；
- AI 自动制定学习顺序、计划、任务或掌握度；
- 默认主动拓展用户未请求的知识；
- 每日强制生成完整学习文章；
- 一个专题下管理多篇不同目的的正式文档；
- 无字幕视频转写和视觉理解；
- 图片与扫描 PDF OCR；
- 多用户协作、公开发布和团队知识库；
- 依赖 Obsidian、飞书或其他第三方产品才能工作；
- 自动跨设备云同步。

### 9.3 后续验证，不纳入承诺

- 知识版图作为注意力导航界面；
- 本地轻量模型承担聚类、去重和敏感检测；
- 视频平台已有字幕的导入和时间引用；
- 飞书文档导出或移动端阅读；
- 更细的联网研究授权梯度；
- 专题数量增长后的归档和维护策略；
- 多文档、多视角或教学型文档生成。

## 10. 验收场景

### 场景 A：连续自由收集

1. 用户从网页右键收集三段内容，并从 AI 对话粘贴两段内容。
2. 每次采集均在数秒内完成，不要求分类，不因 AI 排队而阻塞。
3. 所有内容可在“全部材料”找到并恢复来源。
4. 用户可在批量整理前编辑或删除其中一条内容。

### 场景 B：近期方向形成

1. 系统在合适时机批量整理近期材料。
2. 相关材料形成临时分组，每组只有名称、概括和材料范围。
3. 不相关材料保持独立，不被强行写成统一主题。
4. 用户仅浏览分组不会产生永久专题。

### 场景 C：专题文档生成

1. 用户选择一个临时分组并保存为专题。
2. 用户可检查并调整专题包含的材料。
3. 用户触发生成专题整理文档。
4. 文档忠实归纳材料、去重、呈现差异并提供引用。
5. 关键结论完成集中核验；无法核验的结论带不确定性说明，但文档仍能生成。
6. 材料缺口默认折叠，不生成学习任务。

### 场景 D：持续更新

1. 新材料被建议加入已有专题，但不会自动加入。
2. 用户确认后，专题提示主文档存在可用更新。
3. 用户预览影响并生成新版本。
4. 用户编辑内容未被覆盖，旧版本仍可恢复。

### 场景 E：数据控制与成本

1. 用户禁用某条材料的云端处理，该材料只进行本地保存和解析。
2. 云模型失败不影响原始材料和已有文档版本。
3. 设置页能查看本月 token、费用、调用目的和失败次数。
4. 用户可以导出数据，并明确知道数据存储位置。

## 11. 成功指标

### 11.1 收集效率

- 网页右键到成功反馈的目标时间不超过 2 秒；
- 桌面端从呼出到提交可以在 5 秒内完成；
- 采集成功率不依赖模型成功率；
- 重试不会产生重复材料。

### 11.2 整理价值

- 用户能在 30 秒内理解近期主要收集方向；
- 临时分组不强行吸收明显无关材料；
- 用户生成专题文档前可以清楚看到材料范围；
- 文档中的关键陈述可以回到原始材料；
- 生成失败不会破坏已有文档版本。

### 11.3 产品理解

- 新用户无需理解内部技术术语即可完成完整闭环；
- 用户能够区分“原始材料”“近期收集”“专题”和“专题文档”；
- 用户不会把临时分组误解为系统认定的客观知识分类；
- 用户知道 AI 整理依据哪些材料，以及何时使用了云模型。

## 12. 决策完成度

本 PRD 已确认以下产品级边界：

- 两个核心价值：低摩擦收集与材料整理；
- 四种用户可见知识形态；
- 自动产物为动态的近期收集，而非每日文章；
- 用户触发产物为材料整理型专题文档；
- 每个专题首版只有一篇主文档及版本历史；
- 原始材料是溯源记录，不是已验证事实；
- 关键结论在文档生成时集中核验；
- AI 不主导学习路径；
- 不建设永久语义关系和用户可管理的知识点网络。

尚未确认的事项均已放入“后续验证”，不得阻塞首版实现，也不得在没有新证据时重新进入核心范围。
