# Collector 多模型实施协作协议

协议 ID：`COLLAB-PROTOCOL`

协议版本：`1.2.0`

生效日期：2026-07-17

状态：当前长期协作规则

## 1. 目标

Collector 的前端与后端由不同模型分工，并可能在多个开发轮次中反复交接。本协议用于保证：

- GPT-5.6 持续负责后端、数据、安全、任务恢复和整体产品工程走向；
- KIMI 3 持续负责 WebUI、浏览器交互、视觉实现和前端验证；
- 每次责任转移都有可验证的输入、输出和状态；
- 后续模型优先读取本轮变化，不重复读取未变化的长文档；
- 文档随代码持续更新，但当前共识、当前状态和历史记录保持分离；
- 未验证的能力不会因为交接描述而被误认为已经实现。

## 2. 文档分层

协作文档分为四层。每层只承担一种职责。

| 层级 | 文件 | 内容 | 读取频率 |
| --- | --- | --- | --- |
| 长期规则 | `AGENTS.md`、本文 | 沟通、工程边界、协作流程和交接质量门槛 | 首次参与或版本变化时完整读取 |
| 角色基线 | `docs/FRONTEND_IMPLEMENTATION_HANDOFF.md` 等 | 某一角色长期有效的范围、设计和契约 | 首次接手、版本变化或本轮明确要求时读取 |
| 当前状态 | `docs/handoffs/CURRENT.md` | 当前切片、责任人、待消费交接、本轮必读、阻塞和下一步 | 每次实施任务开始时读取 |
| 单次增量 | `docs/handoffs/H-*.md` | 某一轮相对基线的实际变化和验证证据 | 只读取 `CURRENT.md` 指定的待消费文件 |

`docs/handoffs/INDEX.md` 只保存历史摘要和状态。日常接手不需要阅读全部历史。

## 3. 角色边界

### GPT-5.6

长期负责：

- 纵向切片顺序、领域边界和整体工程框架；
- 共享契约、运行时校验和兼容策略；
- SQLite、迁移、事务、文件和恢复；
- HTTP、SSE、认证、Host/Origin 和安全边界；
- 模型网关、后台任务、搜索和本地观测；
- 后端单元、集成、持久化和重启恢复验证；
- 审查 KIMI 3 回交的前端是否符合真实接口和产品框架；
- 把下一轮所需的后端能力和接口变化增量交给 KIMI 3。

### KIMI 3

长期负责：

- `apps/web` 工程、组件、路由、样式和客户端状态；
- API 客户端、SSE 客户端、草稿和页面恢复；
- 空、加载、失败、离线、认证过期和重试状态；
- 响应式、键盘、焦点、减少动态效果和可访问性；
- Playwright、真实浏览器、控制台、网络和截图验证；
- 把真实浏览器中发现的契约缺口、后端阻塞和产品风险增量交给 GPT-5.6；
- 回交时提供可复现证据，不只说明“页面已完成”。

### 共同规则

- 角色边界不代表不能修改对方区域。跨边界修改必须在交接中单独列出原因、风险和审查人；
- 前端不自行复制或改变共享契约；后端不以静态页面代替真实 WebUI 验收；
- 接口或产品共识需要改变时，先记录变更提案和受影响范围，再修改稳定基线；
- 自动化测试使用隔离数据和确定性假模型。真实云调用需要用户明确授权；
- 按结果提交，不按操作步骤提交。每个提交对应一个可验证、可审查、可独立回滚的任务边界，并只包含本轮相关改动；
- 同一任务中的中间小修和同一责任转移中的动态文档更新合并处理，保留工作区中的其他用户变化。

## 4. 交接编号与状态

### 编号

单次交接文件使用：

```text
H-YYYYMMDD-NNN-FROM-TO.md
```

示例：

```text
H-20260717-001-GPT56-TO-KIMI3.md
H-20260718-002-KIMI3-TO-GPT56.md
```

`NNN` 在仓库内持续递增，不按日期重新开始。

### 状态

每份交接使用以下状态之一：

| 状态 | 含义 |
| --- | --- |
| `prepared` | 交出方已写完，但代码或文档尚未全部提交 |
| `pending` | 已提交，等待接收方确认 |
| `accepted` | 接收方已核对仓库和交接内容，开始工作 |
| `superseded` | 后续交接已替代该交接的当前作用 |
| `blocked` | 接收方无法继续，阻塞原因已写入当前状态 |

交出方完成提交后，把交接设为 `pending`。接收方开始实质开发前核对交接，并在第一笔实质提交或本轮最终交接提交中把它设为 `accepted`。接收后不继续开发、发现阻塞或状态需要立即留档时，才单独创建一笔交接状态提交。交接状态没有更新前，不宣称责任已经完成转移。

## 5. 最小读取算法

每个模型开始实施时执行：

1. 读取根目录 `AGENTS.md`；
2. 读取 `docs/handoffs/CURRENT.md`；
3. 读取其中“本轮必读”的交接文件和指定章节；
4. 查看 `git status`、最近提交和本轮相关源码/测试；
5. 只有以下情况才完整读取长期协议或角色基线：
   - 首次参与该角色；
   - `CURRENT.md` 标记版本变化；
   - 本轮必读明确要求；
   - 当前上下文无法确认稳定边界；
6. `CURRENT.md` 明确写着“版本未变化”的长文档不重复读取；
7. 历史问题只按交接编号查询 `INDEX.md`，不顺序阅读全部历史交接。

新模型没有上一轮上下文时，至少读取当前角色基线一次。相同角色连续工作且基线版本未变化时，只读取当前状态和新增交接。

## 6. 基线版本与变化提醒

每份角色基线在文首保存：

- 基线 ID；
- 版本号；
- 最后更新日期；
- 适用角色；
- 当前状态文件链接。

版本规则：

| 变化 | 版本动作 | 接收方阅读要求 |
| --- | --- | --- |
| 文案澄清、不改变行为 | Patch | 只读交接列出的变化章节 |
| 新增范围、状态或接口 | Minor | 阅读变化章节及其依赖章节 |
| 产品边界或架构方向改变 | Major | 重新完整读取该基线 |

交接文件必须填写“基线变化”：

- `none`：长期规则未变化；
- 文件、旧版本、新版本、变化章节；
- 是否需要完整重读；
- 变化原因和影响。

`CURRENT.md` 同时保存当前有效版本和本轮必读列表。它是持续更新提醒的唯一入口。

## 7. 一轮协作生命周期

### 7.1 接收

接收方：

1. 按最小读取算法加载上下文；
2. 对照提交哈希检查实际文件；
3. 复跑与风险相称的最小验证；
4. 发现描述与代码不一致时，先把差异写入当前状态；
5. 核对待消费交接后开始实质开发，并按第 4 节规定合并记录 `accepted` 状态。

### 7.2 实施

实施方：

- 只处理本轮范围；
- 保持接口、数据和用户可见状态一致；
- 记录偏离基线的决定，不把临时实现写入长期共识；
- 发现对方角色阻塞时，立即记录到 `CURRENT.md` 的“需要对方处理”，不等到最后才说明；
- 任何安全、数据丢失或契约破坏风险优先通知对方。

### 7.3 验证

验证默认采用能够覆盖本轮风险的最小级别，不因完成文件修改自动运行全量构建和全部测试。

| 级别 | 适用改动 | 必须验证 | 默认不要求 |
| --- | --- | --- | --- |
| 一级：文档 | 纯文档、文案、交接状态、版本或元数据 | 格式、链接与引用、版本一致性、差异和提交范围 | 代码构建、代码测试、浏览器测试 |
| 二级：前端 | 局部 WebUI、样式、组件、客户端状态或交互 | 前端构建或类型检查、受影响测试；用户可见交互增加真实浏览器及相关视口、键盘、可访问性、控制台和网络检查 | 无关后端全量测试 |
| 三级：后端 | 局部 API、服务、任务、持久化或恢复逻辑 | 后端构建或类型检查、受影响的单元、集成、API、持久化或重启恢复测试 | 与改动无关的浏览器测试 |
| 四级：全量 | 共享契约、迁移、构建配置、跨端集成或发布 | 全量构建、全量测试、项目检查；有用户可见路径时增加浏览器端到端验证 | 无 |

选择与升级规则：

- 同一轮包含多类改动时，采用其中最高级别；
- 涉及认证、安全、数据丢失、数据库迁移、影响范围不确定，或当前级别验证失败时，至少提升一级；必要时直接提升至四级；
- 接收方复跑验证时也按风险选择级别，不默认重复交出方全部命令；
- 按本表跳过无关检查属于有意控制验证范围，必须记录原因，不视为遗漏。

交出方至少记录：

- 所选验证级别和选择原因；
- 实际运行的命令；
- 通过、失败、跳过数量；
- 跳过原因；
- 是否调用真实云模型；
- 是否完成真实浏览器验证；
- 是否验证 API/SQLite 可见结果；
- 未验证的内容和原因。

### 7.4 交出

交出方必须：

1. 从模板创建新的增量交接文件；
2. 只写本轮变化，不复制未变化基线；
3. 更新 `INDEX.md`；
4. 更新 `CURRENT.md` 的当前责任、待消费编号、本轮必读、阻塞和下一步；
5. 如长期规则变化，更新对应基线版本和变化章节；
6. 按任务边界提交：代码、测试和直接相关的长期文档进入同一笔实现提交；只有交接文档需要引用已经生成的实现提交哈希时，才增加一笔相邻交接提交；
7. 每次责任转移最多创建一笔交接提交，并在其中一次性更新新交接文件、`CURRENT.md`、`INDEX.md` 和相关接收状态；
8. 报告相关实现提交与交接提交哈希，以及工作区中保留的其他变化。

## 8. GPT-5.6 交给 KIMI 3 的必填内容

- 本轮用户可见目标和明确非目标；
- 已实现的后端能力、提交哈希和文件范围；
- 共享类型名和变更；
- HTTP/SSE 路径、状态码、事件续传和错误语义；
- 认证、Cookie、Host/Origin 和安全限制；
- 数据迁移、恢复语义和幂等要求；
- 开发启动方式、假模型和隔离数据配置；
- KIMI 3 可以立即开始的内容；
- 尚未就绪、不得伪造的能力；
- 必须覆盖的页面状态和浏览器验收；
- 需要 KIMI 3 回传的证据；
- 基线变化和本轮最小必读列表。

## 9. KIMI 3 交给 GPT-5.6 的必填内容

KIMI 3 完成前端工作后，回交必须包含以下内容。

### 用户可见结果

- 用户现在可以完成的完整路径；
- 空、加载、成功、失败、离线、认证过期和恢复状态；
- 未完成或仅占位的界面；
- 与交接目标存在的差异及原因。

### 代码与依赖

- 提交哈希、分支和修改文件范围；
- 新增或升级依赖及原因；
- 前端路由、组件和状态边界；
- API/SSE 客户端的关键行为；
- 是否修改共享契约、后端或构建脚本；
- 任何临时兼容层、假数据或技术债。

### 接口核对

- 实际调用的每个接口和状态码；
- 与共享契约不一致的字段；
- SSE 重连、事件去重和最终状态确认结果；
- 401、403、404、500、任务错误和断线表现；
- 需要 GPT-5.6 修改的后端缺口，附复现步骤和期望契约。

### 浏览器证据

- 使用的浏览器与视口；
- 320、768、1024、1440 像素结果；
- 页面截图或测试产物位置；
- 键盘操作、焦点顺序和 Escape 行为；
- 可访问名称、标题层级、动态通知和减少动态效果；
- 控制台错误与警告数量；
- 关键网络请求、状态码和重复请求情况；
- 刷新、关闭页面和重新打开后的恢复结果。

### 数据与安全

- WebUI 动作对应的 API 和 SQLite 可见结果；
- 草稿、会话和任务的恢复验证；
- 是否出现 token、Cookie、API Key 或私人内容泄露风险；
- 不可信 AI/来源内容的渲染方式；
- 是否使用真实云模型以及用户授权情况。

### 验证与剩余风险

- 每条实际运行命令和结果；
- 失败、跳过和未运行项；
- 已知缺陷、复现步骤、影响和临时绕行；
- 推荐 GPT-5.6 优先处理的后端或框架事项；
- 回滚方式或安全禁用方式；
- 基线变化和下一轮最小必读列表。

缺少真实浏览器证据、接口核对或恢复验证时，前端交接不能标记为完成，只能标记为部分完成或阻塞。

## 10. 动态文档维护规则

### 每轮必须更新

- 新增一份 `H-*.md`；
- 更新 `CURRENT.md`；
- 更新 `INDEX.md`；
- 交接文件状态与当前责任保持一致。

以上内容属于同一交接边界，必须合并到同一笔交接提交或本轮唯一的实现提交中，不分别提交。

### 有变化才更新

- 角色基线；
- 产品共识；
- 架构文档；
- 人工验收标准；
- 本协议版本。

### 不进入基线的内容

- 本轮命令输出全文；
- 临时排查过程；
- 已放弃方案；
- 未确认猜测；
- 只对单次提交有效的文件清单；
- 已经由后续实现替代的限制。

这些内容进入单次交接或历史索引，避免长期文档持续膨胀。

## 11. 当前状态文件质量门槛

`CURRENT.md` 始终保持短小，并必须包含：

- 当前切片；
- 当前责任角色；
- 下一接收角色；
- 当前基线版本；
- 待消费和最近已消费交接；
- 本轮必读；
- 可以立即开始；
- 阻塞和需要对方处理；
- 完成前更新提醒。

当内容超过约 200 行时，把历史内容移动到交接文件或 `INDEX.md`，当前状态只保留仍然有效的信息。

## 12. 完成定义

一次模型协作只有同时满足以下条件才完成：

- 本轮代码或文档已按定义的实现边界或交接边界提交；
- 相关验证完成并记录；
- 新交接文件存在；
- `CURRENT.md` 指向正确的下一责任角色；
- `INDEX.md` 状态正确；
- 基线变化已明确为 `none` 或记录版本升级；
- 用户和下一模型都能区分已实现、待实现、阻塞和未验证内容；
- 工作区中的其他用户变化没有被混入提交。
