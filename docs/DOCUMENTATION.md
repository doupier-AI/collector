# 文档维护规则

本文件规定 Collector 文档分别记录什么，以及修改文档时如何保持唯一、当前、可执行的答案。

## 事实分工

1. `docs/product/` 记录已经确认的产品含义、边界和不变量。
2. 源码、共享契约、迁移、自动化测试和实际界面说明当前实现。
3. 当前任务描述说明本次获准改变的范围。
4. Git、GitHub Issues 和必要的决策记录保存历史与例外追溯。

产品契约不证明功能已经实现，现有代码也不自动证明其产品含义已经得到确认。两者冲突时，应先判断是实现缺口、遗留代码还是契约缺失；无法唯一判断的内容保持待确认。

## 只记录当前有效状态

- 现状文档只写当前有效的事实、规则、决策、边界和使用方式，使读者可以直接据此理解或执行。
- 修改时直接替换或删除过时内容，不在旧内容后追加纠正、多代口径、开发经过或临时状态。
- 形成原因、讨论过程、旧方案和已废弃行为不进入现状正文。
- 历史只有在审计、迁移、兼容或安全追溯确实需要时才保留，并放入明确标注日期、范围和状态的历史载体。
- 个别反例只有仍会改变当前规则、操作或风险判断时才记录。
- 写入前检查每段内容能否帮助当前读者正确理解或执行；不能产生这一作用的内容删除。

## 内容归属

- `README.md`：产品定位、启动方式、主要使用入口和文档索引。
- `docs/product/`：稳定产品契约，不记录实现进度、提交、Issue、测试数量或开发经过。
- `docs/ARCHITECTURE.md`：稳定技术结构、依赖方向、数据与安全边界、代码导航。
- `docs/ENGINEERING.md`：实施、验证、并行协作、提交和集成规则。
- `docs/ACCEPTANCE.md`：用户明确触发的人类拟真验收流程。
- Git 与 GitHub Issues：历史过程、已关闭任务和一次性例外；仓库不维护重复的手写进度总表。

同一事实只保留一个权威解释。其他文档需要提及时使用短指针或面向其读者的必要摘要，不复制完整规则。

## 新概念与不确定性

- 未经用户确认的新功能、关系、状态、权限、自动行为和默认行为只保留在当前任务中，不能写成现行产品契约或据此继续扩张实现。
- 历史代码、旧文档、旧 Issue、原型和内部字段只能作为线索，不能代替当前产品决定。
- 更晚的明确用户决定与当前代码、测试能够唯一消解冲突时，直接更新现状文档；仍存在多种合理含义时保持待确认。

## 何时更新

- 产品含义发生已确认变化时，更新主责产品模块。
- 技术依赖或稳定边界变化时，更新架构文档。
- 启动、配置或主要使用方式变化时，更新 README。
- 实施或验证流程变化时，更新工程文档。
- 普通功能实现、重构或缺陷修复不自动产生产品文档、进度文档或决策记录。
