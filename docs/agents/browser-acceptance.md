# 浏览器体验验收流程（Chrome DevTools MCP 真浏览器）

自动化测试（Playwright e2e、vitest）证明"契约正确"：给定操作得到正确结果。本流程证明"体验成立"：第一次使用的人能否走通、会不会困惑。两者分工，不互相替代——选区交互死循环（2026-07-30 用户发现）就是全量 e2e 通过但体验不成立的实例。

验收内部分两级漏斗：验收代理在真实浏览器中尽量多地发现疑点并做全方位评价；独立审查代理对原始问题清单逐条复跑复核——只有第二轮确认成立的问题才呈现给用户。

## 何时执行

- 涉及用户可见交互的切片完成后（如阶段 H 修订票据落地）；
- 发布前；
- 真实模型环境恢复后的真实验收。

## 两条轨道，按目的选择

- **确定性演示轨道**（`npm run launch:mvp` 或快速演示入口）：回答为本地确定性模拟，每条带"本地演示回答｜非真实 AI｜未联网检索"指纹。测交互、鲁棒性、恢复、响应式时优先这条——结果可复现，不依赖密钥与网络。模拟回答不是产品能力证据。
- **正式真实模型轨道**（双击 `Collector.cmd` 或 `npm run launch`；已配置模型时走真实供应商，`Collector-真实模型.cmd` 为带环境变量的启动器）：测回答质量、真实选区理解、联网搜索时才用这条。未配置模型时进入"模型未配置"状态，本身就是验收场景之一（见流程第 10 步）。

## 纪律

- 把自己当作第一次使用 Collector、不了解页面结构的新用户；
- 不要读取现有自动化测试来照着操作；
- 不要把"测试通过"当作体验通过——功能最终完成但过程令人困惑，同样记录为体验问题；
- 不要立即修改代码，先输出完整问题清单；
- 原始问题清单不直接呈现给用户：所有问题必须经独立审查代理第二轮复核（第 15 步之后的审查机制），确认成立后才进入最终报告。

## 当前产品形态速览（验收依据）

统一节点页（`/research/:sessionId/node/:nodeId`）承载对话与文档阅读；选中文字后**选区上方出现浮动胶囊**（含【引用】按钮），点击【引用】后**引用态胶囊进入输入框区域**，发送分「在此追问」（当前节点对话流）与「深入研究这段」（创建子节点并导航）两种模式；快捷键 `t` 唤出全屏树导航；旧选区智能窗口（AI 分析面板与难度/时长等字段）与旧"稍后再学"入口已整体退役；用户标记与笔记（【标记】按钮 + 笔记输入框）在 issues #12/#13 重建中，尚未上线。

## 验收流程

使用 Chrome DevTools MCP 在真实可见浏览器中操作：每个关键页面查看实际画面并截图；全程留意控制台错误、失败请求、重复请求、页面卡顿和刷新后数据丢失。

### 1. 启动与配对

双击启动器（或运行轨道对应命令）后，默认浏览器打开 `127.0.0.1:<动态端口>`；确认地址中不含令牌或配对码；重复启动同一版本复用同一服务与端口。

### 2. 从提问开始研究（Chat 入口）

在开始页输入一个问题并提交，进入节点页，确认 AI 回答流式出现、模型状态可见。以新用户视角记录：入口是否明显、等待有无反馈。

### 3. 导入文档并阅读

导入一份 TXT 或 Markdown（条件允许再试 DOCX / PDF），进入阅读页，确认正文完整、导入状态有反馈。尝试在导入过程中离开再返回。

### 4. 选区与浮动胶囊（节点页）

在 AI 回答中选中一段文字：

- 浮动胶囊应出现在**选区上方**（空间不足时在下方），含【引用】按钮；
- **点击选取文字以外的屏幕区域**，胶囊与选区消失；重新选取应再次出现；
- 按 Escape——**不应**关闭胶囊或清除选区（这是明确的产品规则，Esc 关闭属缺陷）；
- 只选中一个字：同样出现胶囊，**不应**有任何"选区太短"提示；
- 键盘选择（Shift + 方向键）也应触发胶囊。

### 5. 引用与双模发送

点击【引用】：浮动胶囊关闭，引用态胶囊（选区文本截取 + 移除按钮）出现在输入框区域。

- 此时点击输入框、输入文字——**引用不得消失**（历史死循环缺陷：聚焦输入框导致选区状态丢失）；
- 输入问题后分别验证两种发送：「在此追问」——消息进入当前节点对话流，不产生新节点；「深入研究这段」——创建子节点并导航过去；
- 两个按钮的视觉区分是否清楚、文案是否看得懂；
- 移除引用后发送应回到普通对话。

### 6. 来源返回与刷新恢复

在子节点页面：

- 顶部来源条展示来源内容名与选区摘要；点击"返回原文"回到来源节点，原选区被高亮圈出；
- 刷新页面：节点内容、来源关系、`?sel=` 高亮均应恢复。

### 7. 全屏树导航

按 `t` 或顶栏按钮唤出全屏树导航：面包屑路径正确呈现父子层级；方向键在节点间移动；进入子节点、跳回兄弟节点；关闭方式符合界面提示。多层树（至少三层：根 → 子 → 孙）下验证导航是否迷路。

### 8. 阅读页选区一致性

在导入文档阅读页选中一段快照文字：浮动胶囊行为应与节点页一致（上方出现、【引用】、双模发送可用、Esc 不关闭）；阅读页产生的子节点返回原文时回到阅读页并恢复高亮；刷新后 `?sel=` 在阅读页同样恢复。

### 9. 模型设置

进入 AI 模型设置页：新建配置（供应商、模型、Key 暗文 + 眼睛切换）、测试连接（显示耗时）、保存并启用、获取模型列表、按任务类型分配模型。确认 Key 不出现在界面明文与日志中。

### 10. 未配置模型与失败状态

在无任何模型配置的状态下（可用全新数据目录）：提交问题应看到清楚的失败原因与重试入口，而不是空白或假数据；选区引用与节点操作在模型不可用时仍应可用（引用、返回、导航不依赖模型）。

### 11. 联网搜索开关（配置模型后）

输入框联网开关默认关闭；关闭时回答不呈现外部来源并如实说明；开启后请求供应商联网能力（供应商不支持时如实说明未获得可核验来源，不得编造）。

### 12. 鲁棒性

刷新、浏览器后退/前进、快速重复点击【引用】与发送按钮（不得产生重复选区记录或重复消息——幂等）、空输入提交、超长输入、生成中途离开再返回、错误状态重试。每一步后确认数据没有丢失。

### 13. 视口与纯键盘

- 宽屏与窄屏（约 375px）：浮动胶囊不溢出视口、引用态胶囊与双模按钮不遮挡输入、树导航可用；
- 纯键盘走一遍主路径：Tab 聚焦胶囊按钮、Enter 触发、输入框可达、树导航方向键操作。

### 14. 退役项与重建项核对

- **不应存在**：旧选区智能窗口（AI 分析面板）、difficulty / quickReadMinutes / deepStudyMinutes / prerequisites / relationToFocus 等字段、旧"稍后再学"入口（星级、AI 概括）；发现任何残留入口即缺陷；
- **暂不存在（重建中）**：选区胶囊上的【标记】按钮与笔记输入框、标记列表——issues #12/#13 完成后，在此补充流程：点击【标记】立即保存 → 输入框向右展开、选区文本浅色提示 → 1 秒不点击自动收起（纯标记）→ 点击输入框后固定于屏幕位置、滚轮滑动不移动 → 点击屏幕其他位置保存关闭（Escape 不关闭）→ 标记列表呈现原文/笔记/来源/时间 → 点击标记返回原文高亮。

### 15. 全方位评价（美观 · 舒适 · 完整）

走完流程后跳出"找错"视角，以新用户的第一印象对产品做整体评价，写入评价章节（与问题清单分开）：

- **UI 美观度**：布局与留白、信息层次、字号与对比度、配色与组件视觉一致性（胶囊、按钮、来源条、树导航、设置表单）、宽屏与窄屏下的视觉观感。每一点附截图。
- **交互舒适性**：每个操作的反馈及时性（加载、成功、失败状态有无空窗）、操作成本与容错、过渡是否自然、选中文字与操作胶囊/输入框的手感、文案是否一读就懂。
- **功能完整性**：逐条对照 `docs/PRODUCT.md`"当前能力"——每项承诺的能力都应有可达入口与走得通的闭环；"文档写了但找不到入口""入口在但流程断掉""半成品状态暴露给用户"都要记录。

每条评价必须标注性质：**客观问题**（错位、缺状态、流程断、入口缺失）并入问题清单走审查；**主观建议**（更美观、更顺手、更醒目的改进提议）单独列出、注明"建议，非缺陷"，不计入问题清单。

## 审查机制（第二轮复核）

原始问题清单（含第 15 步并入的客观问题）呈现给用户之前，必须由独立审查代理完成第二轮复核。**不得跳过审查直接把问题交给用户核对。**

- **绝对客观，不偏袒任何一方**：审查代理不代表任何立场——既不帮验收方"多确认问题"，也不帮产品/实现方"少确认问题"。判据只有两个：真实浏览器中的复现事实、产品文档（`docs/PRODUCT.md`、`docs/HUMAN_ACCEPTANCE_STANDARD.md`、对应规格/票据）中的既有共识。没有复现事实或文档依据支撑的印象、猜测、"感觉不太好"一律不作为判据。
- **强制反方检验**：每条裁决先写出反方最强理由，再写正方理由——确认成立的问题必须回答"这为什么可能不是问题"；被驳回的问题必须回答"这为什么可能是真问题"。若反方理由比正方更充分，裁决翻转。写不出反方理由的条目不得裁决。
- **证据持平的处理**：复现事实与文档依据都不充分、又无产品共识时，不判"确认成立"，归入"待用户定夺"并如实列出双方疑点——宁可少报，不可把未经证实的问题交给用户核对。
- **独立上下文**：审查代理是新调用的代理，不共享验收方的结论与信心，只接收问题条目及其复现步骤、截图、实际/预期描述后独立判断——避免"自己发现的越看越对"的确认偏误。
- **实际复跑**：对每条问题，审查代理用 Chrome DevTools MCP 在真实可见浏览器中重新执行复现步骤。复现得到判"确认成立"；复现不到判"不成立"并记录复跑时的实际现象。不允许只读描述做文字判断。
- **依据核对**：对照 `docs/PRODUCT.md`、`docs/HUMAN_ACCEPTANCE_STANDARD.md` 与当前切片对应的规格/票据。符合产品决策的行为不是问题（例如"按 Esc 胶囊不关闭"是明确规则，若被报为缺陷应驳回）；产品文档没有明确共识的，判"待用户定夺"并说明分歧点。
- **合并与定级**：重复问题合并为一条；严重程度（阻断 / 严重 / 一般 / 轻微）重新核定，就高不就低需给出理由。
- **裁决**：每条问题恰好落入四种裁决之一——**确认成立**（附复跑证据与反方检验）、**预期行为**（附产品依据）、**无法复现**（附复跑详情）、**待用户定夺**（附双方疑点，用于证据持平、无产品共识的情形）。

## 输出要求（复核后最终报告）

呈现给用户的最终报告只含三部分：

1. **确认问题清单**（裁决为"确认成立"的条目，按严重程度排序）：每条含严重程度、用户感受、复现步骤、实际结果、合理预期、截图证据；
2. **全方位评价**：美观 / 舒适 / 完整三个维度的结论与截图；主观建议单独成节、注明"建议，非缺陷"；
3. **被筛除条目附录**（从简）：每条一行——条目、裁决（预期行为 / 无法复现 / 待用户定夺）、一句话理由。供用户抽查审查尺度，不附详细证据。

同时汇报：控制台错误与网络异常汇总、各关键页面截图、两条轨道中实际使用的一条及其原因。确认成立的问题按常规流程转为票据或 issue；验收与审查过程均不直接改代码。
