# 人类拟真测试（Chrome DevTools MCP）

本流程验证“真实用户是否能自然完成目标”，与每个开发切片常规执行的组件、集成和 Playwright 自动化测试分工。Chrome DevTools MCP 人类拟真测试是低频的大版本验收，**不会因单张票据完成而自动运行**。

## 唯一触发方式

只有用户主动说出以下触发词时才执行：

- 【进行一次人类拟真测试】：默认执行“版本增量”模式；
- 【进行一次人类拟真测试：功能区名称】：执行指定功能区专项；
- 【进行一次全量人类拟真测试】：执行全部现役功能区。

“帮我看看页面”“完成开发”“运行测试”“做浏览器验证”等普通表达不自动触发本流程。没有触发时，开发阶段按根 `AGENTS.md` 执行对应级别的自动化验证，并记录“人类拟真测试按全局规则未触发”。

## 三种模式

### 版本增量（默认，推荐）

读取[版本验收基线](browser-acceptance/BASELINE.md)，比较基线提交与当前受测版本，只重点覆盖：

1. 基线之后新增或改变的用户路径；
2. 被共享契约、迁移、公共组件、安全边界或数据恢复变化影响的功能区；
3. 基线中标为“需专项复验”或“尚未验证”的能力；
4. 一条能够连接本次变化与稳定能力的最短跨区冒烟路径。

旧版本已经稳定、且没有受到本次变化影响的功能不重复完整测试。

### 功能区专项

用户在触发词后指定一个或多个功能区，只加载相应专项文档。当前功能区：

1. [启动器与模型配置](browser-acceptance/areas/launcher-model.md)
2. [Chat、联网搜索与来源引用](browser-acceptance/areas/chat-search-sources.md)
3. [选区、引用、标记与来源返回](browser-acceptance/areas/selection-mark-return.md)
4. [节点生长、上下文与导航](browser-acceptance/areas/nodes-context-navigation.md)
5. [文档导入与阅读](browser-acceptance/areas/documents-reading.md)
6. [设置、本地观测与数据安全](browser-acceptance/areas/settings-observability-data.md)

用户使用自然语言指定即可，不要求精确复述文件标题。专项测试只覆盖该功能区及其必要前置，不顺带扩展为全量验收。

### 全量

只在用户明确说【进行一次全量人类拟真测试】时执行。全量模式逐一加载六个专项文档，用于重大版本、发布候选版或用户明确要求的全面复核。

## 稳定功能何时需要重测

满足任一条件时，稳定功能可以重新进入范围：

- 用户明确指定它或要求全量测试；
- 它使用的共享契约、数据库迁移、认证、安全、锚点、模型路由或公共 UI 组件发生变化；
- 新功能改变了它的入口、返回路径、持久化或错误恢复；
- 上次验收留下未关闭风险，或当前出现能够指向回归的证据；
- 无法证明它未受本次变化影响。

“已经很久没测”本身不是重复全量测试的理由。

## 受测版本与范围准备

执行前必须：

1. 读取 `docs/PROJECT.md`、相关 ADR、版本基线和选中功能区文档；
2. 确认当前提交、工作区状态、受测启动方式和本次变化范围；
3. 以源码、测试和当前规格裁决实现状态，不把未来 Issue 写成当前功能；
4. 明确本次模式、选中功能区、纳入与排除项、预计使用的轨道；
5. 更新已退役入口或旧文案后再操作，禁止照搬历史流程。

若专项文档与当前产品或源码冲突，先停止并修正文档；不能明知步骤过期仍把界面差异报告成产品缺陷。

## 两条运行轨道

- **确定性演示轨道**：使用隔离端口、临时数据和确定性假模型／假搜索。优先验证交互、恢复、响应式、键盘、可访问性、控制台与网络；模拟结果不能证明真实模型质量。
- **真实模型轨道**：使用普通启动器与本机已保存的可用模型配置。只在范围涉及真实回答质量、模型恢复或真实联网时使用；API Key 不进入截图、日志、文档或对话。

模式决定“测什么”，轨道决定“用什么环境测”；两者不能互相替代。

## 共同执行纪律

- 把自己当作第一次使用 Collector、不了解页面结构的新用户；
- 不按自动化测试脚本机械复刻路径，先从界面理解可发现性；
- 每个关键页面查看实际画面，留意布局、等待反馈、错误恢复和操作成本；
- 全程检查控制台错误、失败请求、重复请求、页面卡顿和数据丢失；
- 覆盖本次范围需要的宽屏、窄屏、键盘、焦点和减弱动效；
- 不立即修改代码，先形成原始问题清单和全方位评价；
- 使用预制或隔离数据；私人内容只保留最小必要截图并遮盖敏感信息；
- 验收和独立复核均不得绕过登录、付费墙、反爬或其他访问限制。

## 全方位评价

每次测试都对**本次纳入范围**评价三个维度，不对排除区做空泛总评：

- **美观**：布局、留白、层次、字号、对比度、组件一致性和不同视口观感；
- **舒适**：反馈及时性、操作成本、容错、过渡、文案和输入手感；
- **完整**：当前规格承诺是否有可达入口、连续路径、恢复与失败状态。

客观问题进入问题清单；主观改善建议单独列为“建议，非缺陷”。

## 独立第二轮复核

原始问题清单在呈现给用户前，必须由独立审查代理使用同一受测版本和功能区逐条复跑。第二轮只接收问题条目、复现步骤、实际／预期和必要截图，不继承验收代理的结论与信心。

每条问题恰好归入：

- **确认成立**：复跑成功，并有当前产品或规格依据；
- **预期行为**：实际行为符合现行产品决策；
- **无法复现**：按相同步骤未出现；
- **待用户定夺**：现象存在，但当前共识不足以判断。

只有“确认成立”的条目转为 Issue。预期行为、无法复现和待用户定夺保留在简短附录中。

## 最终报告

报告必须包含：

1. 受测提交、日期、触发词、模式、功能区、运行轨道和排除范围；
2. 确认问题清单及复核证据；
3. 美观、舒适、完整三维评价和必要截图；
4. 被筛除条目附录；
5. 控制台与网络异常汇总；
6. 本次覆盖变化、跨区冒烟路径和未测试的稳定区；
7. 对版本基线的更新建议。

验收过程不直接改代码。确认问题按常规流程形成票据；验收完成后更新 `BASELINE.md`，记录每个受测功能区最后通过的提交、范围、轨道和遗留风险。
