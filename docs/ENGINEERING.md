# 工程协作与验证

本文件只在实施、构建、测试、并行开发或合并时读取。产品边界见 `docs/product/`，技术依赖见 `docs/ARCHITECTURE.md`。

## 任务入口

实施前，当前任务上下文必须能独立回答：目标用户结果、明确不做项、不可破坏规则、依赖与基线、允许改动面、验收和验证命令。单会话、串行、低风险任务不补建任务文件或 GitHub Issue；只有跨会话、并行、长期阻塞、外部参与、真实缺陷、发布、安全、迁移或用户明确要求时才使用 Issue。

Issue 只保存一张稳定任务卡、当前真实阻塞和最终证据，不维护过程日志或未来任务树。并行任务卡还要声明占用的产品能力、接口/数据/核心模块/测试设施、计划分支和集成依赖。产品边界变化更新主责模块契约；普通实现取舍进入代码、测试和提交。决策记录仍只用于跨模块、难逆转且存在真实替代方案的决定。

## 工作区与领取

- 根工作区和其 `master` 是用户保留区，Agent 不在其中切分支、开发或集成。会写仓库的任务从最新 `origin/master` 建独立 worktree 和任务分支；只读调查与 Issue-only 决策可以不建分支。
- Windows 工具链最低版本是 Git for Windows 2.53.0.windows.3；项目检查低于该版本时直接失败。每个 worktree 必须在自身目录运行 `npm ci` 并拥有独立 `node_modules`，只共享 `.npm-cache/` 下载缓存。禁止从任何 worktree 通过 Junction、目录符号链接或其他重解析点连接根工作区或其他 worktree。
- 一个 worktree 只属于一个任务。不同任务不得共享未提交状态、数据目录或端口范围；不得切换其他任务 worktree 的分支。
- 开工前检查所有活跃 Issue、Draft PR、分支和 worktree。比较的不只是文件名，还包括用户结果、产品能力、接口、表、共享类型、页面动作和测试设施；与活跃任务语义重复时不得领取。
- 并行任务必须先全局可见。没有统一调度、无法查看其他活跃任务或待集成队列已经积压时，代码 WIP 保持一；只有两个任务的能力和改动面都独立时才允许 WIP 为二。
- 共享契约、迁移、认证、安全、锁文件、构建配置、测试基础设施、同一产品契约、同一核心组合文件和同一产品能力串行。共享边界先集成，再释放依赖它的任务。
- 确定性 Playwright 使用互不重叠的完整 `E2E_PORT_BASE` 范围；真实模型验收隔离 `E2E_API_PORT` 与 worker 范围。模型配置只能通过 `COLLECTOR_REAL_MODEL_DATABASE` 只读指向主目录配置库，运行数据仍放在任务专属目录。

任务首次提交后、准备修改共享测试或视觉基线前、标记待集成前，都重新比较各活跃分支相对共同基线的完整差异。固定声明与真实改动不一致时先收窄范围或停止其中一条任务，不能等到最终合并才处理重复实现。

退役 worktree 前先确认任务结果已经提交或明确放弃、工作树无已跟踪或未跟踪改动，再从另一个工作区执行 `npm run worktree:remove -- --path <绝对路径>`。安全清理会拒绝旧版 Git 和脏工作树、先把重解析点作为叶节点解除，再使用非强制 `git worktree remove`，并确认外部目标仍存在。禁止直接调用 `git worktree remove`、`Remove-Item -Recurse`、`rm -rf` 或等价递归删除处理 worktree。

创建、验证和退役 worktree 前后都记录根工作区 `git status --porcelain`；任何新增删除或修改都视为生命周期故障并立即停止。`npm run check` 必须拒绝缺失的已跟踪文件、共享 `node_modules` 和解析到其他 worktree 的内部 workspace 包。

## 开工与开发验证

- 检查基线、工作树、用户已有改动，以及目标模块的代码入口、调用方和测试；不要从 Issue 或旧文档推断已经实现什么。
- 写第一行业务代码前做约五分钟的最短冒烟：后端检查迁移、受影响测试和一条最短端到端；前端检查构建或类型、受影响组件和一条最短端到端；真实模型改动先检查夹具、配置、端口和直连探针。
- 开发分支只运行受影响测试和风险匹配复核，不重复运行无关完整 gate。纯文档、元数据和不进入业务实现的任务不触发业务冒烟。
- 开发期通用快速反馈使用 `npm.cmd run gate:fast`；浏览器失败分别用 `npm.cmd run test:e2e:functional -- <文件或 --shard>`、`npm.cmd run test:e2e:special` 或 `npm.cmd run test:e2e:visual` 最小复现。
- 提示词、token 预算或模型参数变化先运行适用的 `scripts/probe-*.mjs`。API Key 只从本机安全配置读取，不进入命令输出、截图、文档或对话。

| 改动风险 | 开发分支最小验证 | 最终集成候选 |
| --- | --- | --- |
| 纯文档、规则、文案、Issue/PR 元数据 | 链接、引用、格式、`git diff --check`、提交范围 | 一级验证，不自动运行产品 gate |
| 局部前端 | 构建或类型、受影响组件；交互变化增加相关 Playwright | 进入 `master` 前运行 `npm.cmd run gate` |
| 局部后端 | 构建或类型、受影响单元/集成/API/持久化/恢复测试 | 进入 `master` 前运行 `npm.cmd run gate` |
| 共享契约、迁移、跨端、构建、发布、测试基础设施 | 受影响子集 | `npm.cmd run gate` |
| 认证、安全、数据丢失或影响未知 | 至少提升一级 | `npm.cmd run gate`，并增加风险专项验证 |

迁移修改必须同步迁移版本、`LATEST_SCHEMA_VERSION` 和迁移重放测试。开发期研究数据可以重建，不增加历史兼容分支；供应商配置、密钥、模型路由和设置必须保留。

## 失败归属与公共缺陷

发现测试、构建或视觉失败时，先最小复现；准备修改测试、夹具、阈值或视觉基线前，必须再在当前任务的干净基线上复现。没有证明失败由当前分支引入，就不得顺手修改共享测试设施。

| 复现位置 | 归属与动作 |
| --- | --- |
| 只在当前分支失败 | 当前任务回归，由当前分支修复 |
| 纯 `origin/master` 同样失败 | 公共主干缺陷，暂停集成并创建或复用唯一缺陷任务 |
| 各分支单独通过、组合后失败 | 集成冲突，由唯一集成任务处理 |
| 与代码差异无关且不稳定 | 测试基础设施缺陷，由唯一基础设施任务处理 |
| 测试与代码代表两种合理产品行为 | 保持待确认，带产品契约、代码和测试冲突询问用户 |

公共缺陷以测试名、稳定错误类别、相关资源和基线 SHA 形成问题指纹。统一调度者先查重再指定唯一负责人；其他任务只记录继承失败，不得复制补丁、重拍基线、降低阈值或跳过测试。主干恢复绿色后，所有待集成分支更新到最新主干并重做必要验证。

视觉快照和 Playwright 基础设施按共享资源处理。只有本任务明确批准的界面变化才能更新对应基线，且必须逐图审查；多个任务会改变同一快照时必须串行，或由集成任务在最终候选 SHA 上统一生成。无图环境使用 `npm.cmd run visual:diff -- ...` 或更强证据，不能以“测试过时”代替原因判定。

## 统一集成与门禁

`npm.cmd run gate` 是最终候选的完整本地入口，覆盖项目检查、构建与单元/集成测试，然后用独立端口和结果目录最多并行两条轨道运行主功能分片、隔离场景和视觉基线；所有轨道结束后一次性报告失败。GitHub 在一个 `gate` 任务中只安装一次依赖和浏览器，再复用同一有界并行入口，避免受账户任务并发额度影响而排队串行，也避免单机同时运行五个浏览器导致资源饥饿；新提交会取消同 PR 的过时运行。

- 同一时间只有一个临时集成 worktree。它从最新 `origin/master` 建立，固定本批候选分支、依赖顺序和允许进入的完整文件范围；根工作区不承担集成。
- 功能分支提供用户结果、局部验证、已知风险和未完成项。并行或跨会话任务在首次有效提交后使用 Draft PR 暴露真实差异；转为 Ready 只表示待集成，不表示完整交付。
- 共享契约、迁移、跨端、认证、安全或数据风险在进入候选前，由没有参与实现的只读上下文根据任务卡、完整差异、产品契约和相关调用方复核；复核者只报告问题，任务负责人修复，集成者裁定是否具备候选资格。纯文档和低风险局部改动不为形式上的“独立”重复启动完整审查。
- 集成者按依赖顺序组合兼容的小批次，检查完整差异和调用方后提交最终候选 SHA。开发分支旧 gate 只证明旧文件树，不能替代、排除或补改后的候选树。
- 最终候选在干净 worktree 中提交后，按上表运行一级、受影响或完整验证。同一候选的独立阶段可以并行，但都必须验证同一 SHA；任何失败修补都会产生新 SHA，并使旧证据失效。
- gate 通过后不得再改变受版本控制的文件。推送前重新获取远端状态；`origin/master` 已前进时重新组装并验证，未前进时只推送已验证候选。随后核对远端 `master` 的祖先链确实包含完成提交。
- GitHub 的 `master` 必须启用分支保护并要求 `gate` 状态检查通过；本地结果、管理员权限和用户口头放行都不能绕过服务端门禁。紧急修复同样先形成可审计候选并通过所需检查。
- 集成失败保留候选分支和证据，不把半成品推入主干。长时间命令使用 `npm.cmd run run:logged -- <命令>` 保存完整输出和真实退出码。

## 状态、关闭与记录

正式合并候选的生命周期固定为：开发中 → Draft PR / 待集成 → 已进入远端 `master` → 关闭 Issue。代码写完、局部测试通过、分支推送或 PR Ready 都不能称为完整交付；只有远端祖先关系确认后才能关闭对应 Issue。使用原生 PR 状态表达待集成，不再维护 PROJECT、进度文档或重复状态文件。

明确不合入主干的研究、原型和 Issue-only 决策是例外：按任务规定的证据、用户裁决和处置方式完成后可以关闭，但必须写明“仅证据”“未实施”或等价边界，不能宣称形成生产能力。

提交前检查完整差异、未跟踪文件、相关调用方和测试退出码。一个可验证、可审查、可独立回滚的用户结果形成一次提交；提交、PR 和 Issue 只记录实际变化、验证、偏差、风险与未完成项，不复制产品规格。没有活跃 Issue 的普通任务不补票，没有跨模块难逆决定的任务不补决策记录。
